# Release runbook

This document describes how Continuum is released: the dev-to-master flow,
what the automation does, and how to recover when something goes wrong.

## The big picture

There are two branches that matter:

| Branch   | Role                                                            |
|----------|-----------------------------------------------------------------|
| `dev`    | Integration branch. All work lands here first. Never released.  |
| `master` | Protected release branch. Advances only via squash-merged PRs.  |

`master` is protected: it accepts changes only through pull requests, and the
`build` status check must be green before a PR can be merged. The release
automation never pushes commits to `master`; it only builds what was merged.

Release numbering is derived from the commit count on `master`:

```
N         = git rev-list --count HEAD     # commits on master at merge time
version   = build-<N>                      # e.g. build-137
```

There is no manual version file to bump. `gradle.properties` keeps the local
development version; CI always passes `-Pversion=build-<N>`, which takes
precedence over `gradle.properties`. The Paper plugin descriptor
(`paper-plugin.yml`) and the Velocity plugin descriptor are generated from
`project.version`, so both platforms see `build-<N>` automatically.

Versions are monotonic as long as `master` is linear-ish (squash merges make
history linear). `N` never goes down or repeats while history is intact.

## What runs when

| Workflow                         | Trigger                | Result |
|----------------------------------|------------------------|--------|
| `build.yml`                      | PR + push to `main`/`master`/`dev` | Required PR check (`build`). Not a release. |
| `devbuild.yml`                   | Push to `dev`          | Builds `devbuild-<N>`, channel `dev`, publishes to R2 `dev/devbuild-<N>/`, posts to the dev Discord channel. No tag, no GitHub Release. |
| `release.yml`                    | Push to `master` (+ manual dispatch) | Builds `build-<N>`, creates tag `build-<N>` and a source-only GitHub Release, publishes jars + signed manifest to R2 `release/build-<N>/`, posts to Discord. |
| `compat-ci.yml`                  | Separate pipeline      | Compatibility smoke tests. Not covered here. |

### Docs-only merges: `[no release]`

A push to `master` whose head commit message carries the `[no release]`
tag produces no tag, no release and no Discord post. The release workflow
parses the head commit message with the repository's tag parser
(`tools/ci/tags.py`); when the parser reports `no_release=true`, every
release step is skipped and a notice is logged instead. `build.yml` still
gates the merge as usual. If the parser itself fails, the release proceeds
as normal - the advisory tool cannot block the pipeline. Manual dispatch
re-runs always perform the release. See `docs/ci-tags.md` for the tag
system in general.

## The release workflow, step by step

`.github/workflows/release.yml` runs on every push to `master`:

1. **Guard** — refuses to run anywhere but `master`.
2. **Checkout** with full history (`fetch-depth: 0`); required for the
   commit count and for the changelog.
3. **Compute N** — `git rev-list --count HEAD` (or the `build_number` input
   on manual dispatch; see "Re-running a release").
4. **Verify tag availability** — if `build-<N>` already exists and points at
   `HEAD` and this is a manual re-run, tag creation is skipped; otherwise the
   job fails loudly. Tags are never overwritten.
5. **Build** — `./gradlew build --parallel --stacktrace -Pversion=build-<N>`.
6. **Tag** — annotated tag `build-<N>` is created and pushed.
7. **Release notes** — generated by git-cliff (`orhun/git-cliff-action@v4`)
   from `cliff.toml`, covering the latest tag (`--latest --strip header --no-exec`).
8. **manifest.json** — built with `jq`: build, channel (`release`), commit,
   per-jar `sha256` and `size`, and `builtAt` (UTC).
9. **Signature** — `openssl pkeyutl -sign -rawin` with the Ed25519 private
   key from `R2_MANIFEST_ED25519_KEY`. Verified in-place before upload
   (sign, then verify with the derived public key). Skipped with a notice
   when the secret is absent.
10. **R2 upload** — `aws s3 cp --endpoint-url ... --region auto` of both
    jars, `manifest.json` and `manifest.json.sig` to
    `s3://<R2_BUCKET>/release/build-<N>/`. Skipped with a notice when the R2
    credentials are absent.
11. **GitHub Release** — created with `softprops/action-gh-release@v3`,
    tag `build-<N>`, body from git-cliff. **Source only**: no jars, no
    generated release notes (`generate_release_notes: false`).
12. **Discord** — embed posted to the release channel when
    `DISCORD_WEBHOOK_URL` is configured; skipped with a notice otherwise.

Every secret-dependent step is gated on the secret's presence. Until the
secrets are configured, the pipeline still builds, tags and creates the
GitHub Release; the R2 upload, signature and Discord post are skipped with
clear `::notice::` messages.

## Source only, and why

GitHub Releases carry **no jars** - source code and changelog only.

Continuum is AGPL-3.0 software. Self-building is free forever. The jars are
a convenience for server operators who do not want to run Gradle; selling
ready-made builds is how the project is funded. Publishing jars on GitHub
Releases would give them away to anyone for free and defeat that model, so
the distribution channel for built artifacts is a private Cloudflare R2
bucket, served through the license service.

What this means in practice:

- `softprops/action-gh-release` is configured with **no `files:` key** and
  `generate_release_notes: false`. Do not add assets to it.
- Built jars go to R2 only. The license service presigns download URLs and
  verifies `manifest.json.sig` against the Ed25519 public key.
- The GitHub Release is the anchor for the tag, the changelog and the
  source archive - that is all.

## Cutting a release

1. Merge the work into `dev` as usual (feature branches, squash merges,
   green checks).
2. Open a PR from `dev` to `master`. Title it as a squash-merge commit,
   e.g. `chore(release): build-<N>` or a summary of the included work.
3. Wait for the `build` check. Merge with squash.
4. The `release` workflow runs on the push to `master` created by the merge.
   When it finishes:
   - tag `build-<N>` exists on the merge commit,
   - the GitHub Release `build-<N>` is published (source only),
   - `s3://<bucket>/release/build-<N>/` holds both jars, `manifest.json`
     and `manifest.json.sig`,
   - the Discord channel has the announcement.
5. Verify: open the release, check that the two jars on R2 match the
   `sha256` values in `manifest.json`.

The first release ever works the same way: the changelog generated by
git-cliff for `build-<N>` will cover the whole history (there is no earlier
`build-*` tag to diff against).

## Re-running a release

If the workflow failed after the tag was created, re-run it via
**Actions → release → Run workflow** and pass the `build_number` input.
The `build_number` input must match the existing tag `build-<N>` **and** the
`HEAD` of master. The workflow then skips tag creation, rebuilds, and
re-publishes (the GitHub Release action updates the existing release; R2
objects are overwritten with identical content). Passing a `build_number`
for which no tag exists fails loudly — the input exists only for re-running
an already-tagged release.

Re-running with a wrong `build_number`, or any re-run of a `push` event
when the tag already exists, fails loudly. That is deliberate.

## Secrets

Configure under **Settings → Secrets and variables → Actions**.

| Name                    | Kind    | Purpose                                                   |
|-------------------------|---------|-----------------------------------------------------------|
| `R2_ACCOUNT_ID`         | secret  | Cloudflare account id; forms the R2 endpoint URL.         |
| `R2_ACCESS_KEY_ID`      | secret  | R2 API token, access key id.                              |
| `R2_SECRET_ACCESS_KEY`  | secret  | R2 API token, secret access key.                          |
| `R2_BUCKET`             | variable| Target bucket name (not a secret).                        |
| `R2_MANIFEST_ED25519_KEY` | secret | PKCS8 PEM Ed25519 private key used to sign `manifest.json`. |
| `DISCORD_WEBHOOK_URL`   | secret  | Webhook for the release Discord channel.                  |
| `DISCORD_DEV_WEBHOOK_URL` | secret | Webhook for the dev Discord channel.                    |

`GITHUB_TOKEN` is provided by the runner; no setup is needed. It needs
`contents: write`, which the workflow declares itself.

### Generating the Ed25519 manifest key

```bash
openssl genpkey -algorithm ed25519 -out manifest.key
openssl pkey -in manifest.key -pubout -out manifest.pub
```

- `manifest.key` - the **private** key. Store it as the secret
  `gh secret set R2_MANIFEST_ED25519_KEY < manifest.key` (or paste the file
  contents in the web UI). Never commit it, never paste it anywhere else.
- `manifest.pub` - the **public** key. Give it to the license service; it
  is the verification anchor for everything the release pipeline publishes.
- Destroy local copies securely once the secret is stored.

To verify a downloaded manifest manually:

```bash
openssl pkeyutl -verify -rawin \
  -pubin -inkey manifest.pub \
  -in manifest.json -sigfile manifest.json.sig
```

This prints `Signature Verified Successfully` on success.

### Manifest format

`manifest.json` is the contract between the release pipeline and the
license service:

```json
{
  "build": "build-137",
  "channel": "release",
  "commit": "<full sha>",
  "artifacts": {
    "paper":    { "file": "continuum-paper-build-137.jar",    "sha256": "...", "size": 123456 },
    "velocity": { "file": "continuum-velocity-build-137.jar", "sha256": "...", "size": 123456 }
  },
  "builtAt": "2026-11-19T12:34:56Z"
}
```

Dev builds carry `"build": "devbuild-<N>"`, `"channel": "dev"`.

R2 layout:

```
release/build-<N>/continuum-paper-build-<N>.jar
release/build-<N>/continuum-velocity-build-<N>.jar
release/build-<N>/manifest.json
release/build-<N>/manifest.json.sig
dev/devbuild-<N>/...            (same shape, channel dev)
```

`manifest.json.sig` is the raw 64-byte Ed25519 signature over the exact
bytes of `manifest.json`.

### Where the license service looks

The license service (the piece that sells and serves the jars) is the only
consumer of the private R2 layout. Per build it reads, and nothing else:

```
s3://<R2_BUCKET>/release/build-<N>/manifest.json
s3://<R2_BUCKET>/release/build-<N>/manifest.json.sig
```

It verifies `manifest.json.sig` against the Ed25519 public key (the one
handed to it at setup time), then presigns download URLs for the two jars
in `artifacts` as purchases pass validation. It does the same for
`dev/devbuild-<N>/` when serving dev builds. Nothing else in the bucket is
contractual, and the CI never presigns anything: presigning happens inside
the license service, on every authorized download, so no long-lived
download URL ever exists.

## Rollback

Tags are immutable. There is no re-tagging, no force-push, no "move the
release" escape hatch.

If bad code was released:

1. Identify the last good `build-<N>` tag (it is in the release history).
2. Fix the problem on `dev` and land it.
3. Open the PR from `dev` to `master` as usual; the merge produces
   `build-<N+1>` with the fix.
4. Announce the fix in Discord (or edit the release notes of `build-<N>` to
   point at the fix).

Operators can pin any older build by downloading `release/build-<K>/...`
from R2. The license service keeps old builds; please do not delete them.

If the release pipeline itself is broken (not the code), fix the workflow on
`dev`, merge it, and the next master merge picks the fix up. If the failure
was transient (e.g. Discord outage), use the manual re-run described above.

## Notes for maintainers

- Branch protection on `master` requires the `build` check and squash-merged
  PRs. Do not weaken it to "ship faster" - it is what makes the release
  number trustworthy.
- `build.yml` is the PR gate; `release.yml` does not replace it and does
  not run on PRs. The one CI tag the release workflow consumes is
  `[no release]`; everything else tag-related lives in `docs/ci-tags.md`.
- `compat-ci.yml` (compatibility smoke tests, split out to a separate
  pipeline) is intentionally not part of this runbook.

## What still needs the maintainer

The automation is complete in the repository; what remains is operational,
and none of it can be done from CI:

- **Create the R2 bucket** (e.g. `continuum-releases`) and an API token
  with read/write on it. Store the token as `R2_ACCESS_KEY_ID` /
  `R2_SECRET_ACCESS_KEY`, the account id as `R2_ACCOUNT_ID`, and the bucket
  name as the `R2_BUCKET` *variable* (not a secret — it is visible in logs
  anyway). Until then the R2 upload step skips with a notice.
- **Create the Discord webhooks** on both the release and the dev channel,
  set them as `DISCORD_WEBHOOK_URL` and `DISCORD_DEV_WEBHOOK_URL`. Until
  then the Discord posts skip with a notice.
- **Generate the Ed25519 manifest key** (see above), store the private key
  as `R2_MANIFEST_ED25519_KEY`, and hand the public key to the license
  service. Until then `manifest.json.sig` is not produced and the license
  service cannot verify integrity.
- **Branch protection on `master`**: require a pull request, require the
  `build` check, disallow force-pushes and deletion. `build.yml` is the
  PR gate; it is what makes the release number trustworthy.
- **The license service itself** is a separate project (Bun service reading
  the manifest, verifying the signature, presigning R2 URLs for paid
  downloads). It is documented as a plan, not yet implemented; the R2
  layout and manifest contract in this document are what it will consume.
- **Marketplace listings** (BuiltByBit, Polymart, SpigotMC) stay a
  one-time manual publish of a static jar ($3.99 each); updates do not flow
  through the marketplaces — purchased copies update through the license
  service. The Spigot premium check is weak and should not be relied on.
- **First release rehearsal**: until secrets exist, the first `dev → master`
  PR performs the tag and the source-only GitHub Release, and skips R2 and
  Discord with notices. Configure the secrets first if you want the first
  release to be fully published end to end.
